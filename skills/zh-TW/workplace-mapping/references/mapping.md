# 摸清楚一家新公司或新團隊

新公司的規矩大多沒寫在任何地方。它們散在群組、私訊、會議、別人的提交歷史，還有你被糾正的那一刻。代理每個工作階段都從零開始，沒記下來的就會再問一次、再犯一次。分兩層，不要混：**方法**（這份技能與 `wm`）不含任何公司的資料；**內容**放在那家公司的專案裡。

## 第一天

1. 在工作專案根目錄跑 `wm init --name <公司代號> --lang zh-TW`。它建立下面的目錄、空白範本與 `workplace.toml`。把 `.wm/` 加進 `.gitignore`。
2. 從已經知道的開始填：誰派工、在哪個群收訊息、第一個任務怎麼從開始走到完成。不知道的寫進「待確認」。
3. 把手上已經有的系統、群組、指令登記進 `workplace.toml`（見 `references/environments.md`、`references/commands.md`）。
4. 專案的入口檔（`AGENTS.md` 或 `CLAUDE.md`）加一段：「這是 workplace-mapping 專案，裡面的事一律用 `wm` 指令；從 `wm brief` 開始。」

## 要摸的七類

| 類別 | 要回答的問題 | 用什麼記 |
| --- | --- | --- |
| 人與角色 | 誰負責什麼、誰能拍板、誰開權限；每個人怎麼稱呼、用什麼語言、收什麼形狀的訊息 | `wm card add`、`wm note add --to card:<名字>` |
| 溝通規範 | 哪種事發在哪個群、長度與口氣、什麼要先核准才發、什麼情況要 @ 誰 | `wm note add --to drafting`；機器能檢查的用 `wm rule add` |
| 系統與存取 | 每個系統的入口、怎麼登入、哪台機器連得到、公司會稽核什麼 | `workplace.toml` 的 `[[system]]` |
| 流程 | 一件事經過哪些狀態、誰推進、怎麼證明到了下一步 | `state-machines.md` 裡的一張表 |
| 硬規則與軟慣例 | 違反會出事或被點名的（硬）；照做比較順的（軟） | 每個 skill 最上面的「硬規則」 |
| 節奏 | 上下班、例會、回報期限、發版時段、誰哪幾天不在 | 日常用的 skill |
| 未解的問題 | 還不知道、推論出來沒人證實、兩個來源互相矛盾的 | 每份檔案末尾的「待確認」 |

## 規則怎麼自己長出來

被糾正之後，改的是馬具，不是靠記憶。同一件事分三級往上升：

1. **第一次被糾正**：寫成文字規則，放在人卡或 skill，附來源。一次呼叫：`wm note add "<規則>" --who <誰> --src <出處> --to card:<名字>`。
2. **同一類事第二次被糾正**：文字規則沒擋住，升級成由指令來擋：`wm rule add --id <代號> --from <筆記編號> --message "<該怎麼做>" --when <正則> --require <正則>`。規則可以要求提及某人、要求收據、要求或禁止某種寫法、限制長度，也可以掛任何檢查指令（`--check`）。
3. **規則擋錯了或過時了**：在 `rules.toml` 原地改，寫上日期與改動的來源。不要繞過它。

核准也一樣。使用者說某一類動作以後不用問，就記下來：`wm standing add --id <代號> --kind chat --targets <群的代號> --match <正則> --src "使用者 <日期>：<原話>"`。

每週一次或收工時：合併重複的規則、把散落的事實搬到會被讀到的檔、補缺的來源、清掉已經有答案的待確認。`wm lint` 會列出不一致的地方。

## 一家公司的專案怎麼排

```
<專案>/
  workplace.toml                  名稱、時區、系統、群組、指令
  rules.toml                      送出前的檢查；常態授權
  data/evidence.json              每件事停在哪、驗證收據          （由 wm item、wm receipt 寫）
  worklog/
    YYYY-MM-DD.md                 當天日誌與交接                  （wm log、wm wrapup write）
    commitments.md                答應別人的事                    （wm commitments）
    inbox.md                      每一筆筆記，以及它歸到哪         （wm note）
  .agents/skills/
    <公司>-team/                   人與溝通
      SKILL.md                    硬規則、每個群的用途、什麼事問誰
      references/
        people-cards.md           最上面「擬稿前」清單，下面一人一張卡
        lead-notices.md           負責人交代我方的事，新的在上
        project-<名稱>.md          一個進行中的專案一個檔
        state-machines.md         所有流程的表
    <公司>-dev-release/            倉庫與負責人、分支、版本、建置、發版
    <公司>-daily/                  例會、回報、請假與暫離
```

- 人卡欄位：稱呼、帳號、角色、在哪裡收訊息、語言、收什麼形狀、他通常怎麼回、不要做的、我方對他說過的原話、學到的修正。
- 專案專屬的值（帳號、編號、網址、群名）只放公司專案裡，不放進跨公司的技能。
- 寫到哪分三層：規則與操作方式放 skills 與 `rules.toml`；當下的事實、待辦、承諾放各本帳；換一家公司也成立的教訓，放你自己的跨專案記憶。
- 公司發的規範或手冊，做成一個索引 skill：碰到什麼查哪章、紅線逐條自查、我方還沒符合的列出來（列出不是豁免）。
